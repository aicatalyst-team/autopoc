# 8. Dependency Pinning with Cryptographic Hashes

Date: 2025-03

## Status

Accepted

## Context

Need reproducible builds and protection against supply-chain attacks (compromised PyPI packages, dependency confusion). Standard `pip install` with version ranges is not reproducible and provides no integrity verification.

## Decision

Dependencies are declared in `pyproject.toml` (with version ranges) and pinned in `requirements.lock` generated by `pip-compile --generate-hashes`. The lock file includes SHA-256 hashes for every package.

Install workflow: `pip install -r requirements.lock && pip install -e . --no-deps`.

## Alternatives Considered

- **Poetry**: Heavier toolchain, `poetry.lock` doesn't include hashes by default.
- **pip freeze**: No hashes, includes transitive deps but without reproducibility guarantees.
- **Pipenv**: Slower, less ecosystem adoption for library-style projects.

## Consequences

- (+) Bit-for-bit reproducible installs
- (+) Cryptographic hash verification on every `pip install`
- (+) `pyproject.toml` remains the human-readable source of truth
- (+) CI and local dev use identical pinned versions
- (-) Must run `make lock` after every dependency change
- (-) Lock file must never be edited by hand
- (-) `requirements.lock` filename is non-standard (some tools don't recognize it)
