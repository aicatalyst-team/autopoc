## Project Overview

AutoPoC is a LangGraph-based multi-agent system that automates Proof-of-Concept (PoC) deployments on OpenShift AI. It takes a GitHub repository URL and automatically:

1. Analyzes the codebase to identify components
2. Forks it to GitLab
3. Generates PoC plans with test scenarios
4. Containerizes applications with UBI-based Dockerfiles
5. Builds and pushes images to Quay.io
6. Deploys to OpenShift/Kubernetes
7. Executes PoC validation tests
8. Generates a comprehensive PoC report

The system is designed to be resilient with retry loops for build and deployment failures, parallel execution where possible, and checkpointing for resumable runs.

## Development Setup

### Prerequisites

- Python 3.12+
- podman (for building container images locally)
- kubectl (for Kubernetes operations)
- Access to: GitLab instance, Quay.io registry, OpenShift cluster

### Installation

```bash
make install          # Install pinned deps + editable mode
# or manually:
pip install -r requirements.lock
pip install -e ".[dev,checkpoint]" --no-deps
```

### Configuration

Copy `.env.example` to `.env` and fill in the required credentials:

- **LLM**: Either `ANTHROPIC_API_KEY` or `VERTEX_PROJECT` (for Vertex AI Claude)
- **GitLab**: `GITLAB_URL`, `GITLAB_TOKEN`, `GITLAB_GROUP`
- **Quay**: `QUAY_ORG`, `QUAY_TOKEN`
- **OpenShift**: `OPENSHIFT_API_URL`, `OPENSHIFT_TOKEN`

## Dependency Management

Dependencies are declared in `pyproject.toml` and pinned in `requirements.lock` (generated by `pip-compile --generate-hashes`). The lock file includes cryptographic hashes for supply-chain security.

```bash
make lock             # Regenerate requirements.lock from pyproject.toml
make install          # Install from lock file + editable package
```

**Rules**:
- Add new dependencies to `pyproject.toml`, then run `make lock`
- Never edit `requirements.lock` by hand
- Commit `requirements.lock` changes alongside `pyproject.toml` changes

## Architecture

### Pipeline Flow

The system uses LangGraph to orchestrate a directed acyclic graph (DAG) with conditional routing and retry loops:

```
intake -> [poc_plan || fork] -> containerize <-> build -> deploy -> apply <-> poc_execute -> poc_report -> END
```

Key features:
- **Parallel execution**: `poc_plan` and `fork` run concurrently after `intake`
- **Fan-in**: `containerize` waits for both to complete
- **Build retry loop**: Failed builds retry up to `MAX_BUILD_RETRIES` by looping back to `containerize`
- **Deploy/Apply split**: `deploy` generates K8s manifests, `apply` runs kubectl
- **Apply retry loop**: Failed applies retry up to `MAX_DEPLOY_RETRIES` by looping back to `deploy`

### Agent Types

**Two-phase agents** (procedural then LLM):
- **intake**: Uses `repo_digest.py` for deterministic repo summary, then LLM analyzes it
- **poc_plan**: Tries one-shot JSON generation first, falls back to ReAct if parsing fails

**ReAct agents** (agentic with tools):
- **containerize**: Creates UBI-based Dockerfiles with build context awareness
- **deploy**: Generates Kubernetes manifests (Deployment, Service, Route)
- **poc_execute**: Generates and runs test scripts based on PoC scenarios

**Procedural agents** (no LLM):
- **fork**: Clones from GitHub, pushes to GitLab
- **build**: Runs `podman build` and pushes to Quay
- **apply**: Runs `kubectl apply` on generated manifests
- **poc_report**: Aggregates test results into markdown report

### State Management

All agents read from and write to `PoCState` (defined in `src/autopoc/state.py`). Key state fields:

- **Input**: `project_name`, `source_repo_url`
- **Phase tracking**: `current_phase`, `error`, `messages`
- **Repo analysis**: `repo_digest`, `repo_summary`, `components[]`
- **PoC plan**: `poc_plan`, `poc_scenarios[]`, `poc_infrastructure`, `poc_type`
- **Build output**: `built_images[]`, `build_retries`
- **Deploy output**: `deployed_resources[]`, `routes[]`, `deploy_retries`
- **Test results**: `poc_results[]`, `poc_script_path`, `poc_report_path`

### Checkpointing

Runs are checkpointed using LangGraph's `SqliteSaver` (requires `langgraph-checkpoint-sqlite`). Checkpoints stored in `{WORK_DIR}/checkpoints/autopoc.db`. Resume with `autopoc resume --thread-id <id>`.

## Pattern References

When making common changes, follow these existing patterns:

- **New agent**: Follow `src/autopoc/agents/evaluate.py` — defines an agent function taking `PoCState`, uses tools, returns state updates
- **New tool**: Follow `src/autopoc/tools/file_tools.py` — functions decorated with `@tool`, clear docstring, typed args
- **New CLI command**: Follow `src/autopoc/cli.py` `run` command — uses Typer, loads config, calls graph
- **New prompt**: Add markdown file to `src/autopoc/prompts/` — self-contained with context, tools, output format, examples
- **New test**: Follow `tests/test_intake.py` — mocks external deps, uses fixtures from `tests/fixtures/`

## Important Conventions

### Error Handling

- Agents return `{"error": "..."}` updates to state on failure
- Routing functions check `state.get("error")` to decide next steps
- Build errors can be "permanent" (stop) or retriable (loop back)
- Use `poc_plan_error` for poc_plan failures to avoid state conflicts with parallel fork agent

### Retry Loops

- **Build retry**: `build` fails -> increment `build_retries` -> route back to `containerize` (LLM fixes Dockerfile) -> `build` again
- **Deploy retry**: `apply` fails -> increment `deploy_retries` -> route back to `deploy` (LLM fixes manifests) -> `apply` again
- Retries capped by `max_build_retries` and `max_deploy_retries` config

### LLM Configuration

- Set `ANTHROPIC_API_KEY` for Anthropic API, or `VERTEX_PROJECT` + `VERTEX_LOCATION` for Vertex AI
- Override model per-run with `--model` flag
- Default retry limit is 0 (fail fast on rate limits)

### Logging

Centralized in `src/autopoc/logging_config.py`:
- `--verbose` flag for debug-level output
- Rich formatting for CLI; structured logger for internals
- Long error messages truncated to 200 chars in routing functions

### Working Directory

All operations under `WORK_DIR` (default: `/tmp/autopoc`):
- Cloned repos: `{WORK_DIR}/repos/{project_name}/`
- Checkpoints: `{WORK_DIR}/checkpoints/autopoc.db`

### UBI-based Containers

All generated Dockerfiles use Red Hat UBI for OpenShift compatibility:
- Python: `registry.access.redhat.com/ubi9/python-312`
- Node: `registry.access.redhat.com/ubi9/nodejs-20`
- Go: `registry.access.redhat.com/ubi9/go-toolset`
